# ADR-0003: 渲染器先 GLES3/EGL，Vulkan 后续

- 状态：Superseded by [ADR-0007](0007-vulkan-vulkanpp.md)
- 日期：2026-11-24
- 决策者：powerwm 维护者
- 相关：[architecture.md](../architecture.md)、[testing.md](../testing.md)

> **已被 ADR-0007 替代（2026-11-24）**：项目改为直接采用 Vulkan + 内部 `vulkanpp`，
> 不再使用 EGL/GLES3 作为渲染路径。本文保留作为历史决策记录。

## 背景

合成器需要：

- 在广泛 Linux GPU 上工作（Intel/AMD 开源驱动为主，NVIDIA 尽力支持）。
- 导入 DMA-BUF、处理修饰符、做 damage 区域渲染。
- 支持圆角、阴影、模糊、缩放、色彩空间等效果。
- 可测试（headless）且可替换后端。

候选：EGL/GLES3、Vulkan、软件渲染、wgpu/Dawn 等跨平台抽象。

## 决策

1. **首选后端：EGL + GLES 3.2 + GBM**。
2. 定义薄 `renderer` 接口，不把 GL 类型泄漏到场景层。
3. **Vulkan 作为 Phase 7 之后的可选后端**，在性能数据证明需要时实现。
4. **headless 后端**用于 CI 与金图测试，不依赖 GPU。
5. 渲染效果提供质量档位；帧预算超限时可按策略降级（关闭模糊/阴影/动画）。

## 后果

### 正面

- GLES/EGL 在 Linux 桌面与嵌入式 GPU 上覆盖最广，驱动成熟。
- 与 GBM/DMA-BUF 的集成路径成熟，示例与文档多。
- 开发速度快，便于尽早验证场景图与合成正确性。
- 薄接口允许后续替换/增加 Vulkan，而不改上层。

### 负面 / 代价

- GLES 的状态机与驱动差异需要封装；错误检查成本高。
- 某些现代特性（显式同步、精细内存控制、光线追踪）不如 Vulkan。
- 长期可能维护两个后端，增加测试矩阵。
- 模糊等效果在低端 GPU 上可能触发降级，影响视觉一致性。

### 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 驱动格式/修饰符差异 | 能力探测、格式回退、真实硬件矩阵 |
| 效果成本过高 | 质量档位、帧预算降级、默认保守 |
| 抽象泄漏 | `renderer` 接口只暴露句柄/描述符，不暴露 GL 类型 |
| Vulkan 迁移成本 | 场景与绘制列表与后端无关；金图测试保证行为一致 |

## 备选方案

| 方案 | 优点 | 缺点 | 为何未选 |
| --- | --- | --- | --- |
| Vulkan 优先 | 现代、显式、性能上限高 | 开发成本高、驱动差异大、早期迭代慢 | 先用 GLES 验证产品路径 |
| 软件渲染 | 无 GPU 依赖、确定性好 | 性能不足，无法日常使用 | 仅用于 headless/测试 |
| wgpu/Dawn | 跨平台抽象 | 额外运行时/依赖，C++ 集成复杂 | 不符合原生、轻量目标 |
| Pixman | 简单 | CPU 合成，性能与效果受限 | 仅可作为极端回退 |

## 重新审视条件

- GLES 后端在目标硬件上无法满足帧预算，且优化空间耗尽。
- Vulkan 在目标发行版/驱动上的覆盖率显著提升，维护成本可接受。
- 需要 HDR/显式同步等特性，GLES 路径无法可靠支持。

# ADR-0013: C API wrappers assume the object is valid

- 状态：Accepted
- 日期：2026-11-24
- 决策者：powerwm 维护者
- 相关：[ADR-0009](0009-c-api-wrapping.md)、[coding-style.md](../coding-style.md)

## 背景

早期 C API 封装在 `destroy`、`wait`、`dispatch`、`receive` 等路径中反复检查
`nullptr`、`fd >= 0`、`handle != nullptr`，并让 `raii` 在构造时检查 `valid()`。

这些检查带来三个问题：

- 把“调用者违反契约”伪装成可恢复错误；
- 封装层重复承担生命周期责任，代码噪声大；
- `raii` 无法支持 move-only 或默认构造后未持有资源的类型。

对象合法性的唯一可靠来源是创建路径：`create` 成功即合法，失败返回错误。

## 决策

1. `create` / `open_*` 负责失败检测，返回 `result<T>`。
2. 一旦创建成功，调用者必须保证对象在后续使用和销毁期间合法。
3. 封装层的 `destroy`、方法调用不检查 `nullptr` / `fd` / `handle`。
4. `raii` 不再检查 `valid()`；它只负责“拥有则销毁一次”和移动所有权。
5. `valid()` 可以作为调用者的显式查询保留，但封装内部不得依赖它做防护。
6. 默认构造的 RAII 包装不拥有资源，析构不会调用 `destroy`。
7. 重复 `destroy`、销毁后使用、无效句柄传入属于调用者违约，不保证行为。

## 后果

### 正面

- 封装层更薄、更可读，没有重复防御代码。
- `raii` 支持 move-only / 默认构造但暂不拥有的类型。
- 错误来源清晰：创建失败在 `create`，使用错误在调用者。
- 与 C API 的“前置条件由调用者保证”模型一致。

### 负面 / 代价

- 调用者必须严格遵守生命周期与前置条件。
- 调试无效句柄问题时，崩溃点可能更靠近 C API，而不是封装层。
- 需要更强的测试与代码审查来保证调用顺序。

### 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 调用者传入无效对象 | API 文档、测试、RAII 顺序 |
| 资源泄漏 | `create` + `raii` 固定模式 |
| 过早销毁 | 依赖注入、宿主生命周期契约 |
| 重复销毁 | `raii` 单次所有权；禁止手工重复 destroy |

## 备选方案

| 方案 | 优点 | 缺点 | 为何未选 |
| --- | --- | --- | --- |
| 每个方法检查 valid | 防御性强 | 噪声大、掩盖契约错误 | 与项目模型冲突 |
| 返回错误而不是崩溃 | 可恢复 | 无法真正恢复无效对象 | 伪安全 |
| 使用 `std::optional` 包装句柄 | 类型安全 | 层层解包 | 过度设计 |

## 重新审视条件

- 出现无法通过调用顺序或测试避免的系统性无效句柄问题。
- 封装层需要在不可信插件边界上工作。
